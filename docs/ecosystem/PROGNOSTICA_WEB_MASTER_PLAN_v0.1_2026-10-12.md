Не переименовывать и не переопределять шаги 0–5 без изучения их контрольного плана. Следующую ветку обозначить шагами **6–13**. Исторические коды архитектурной программы **E0–E7** сохраняются как независимые метки соответствия (W6↔E0, W7↔E1, W8↔E2, W9↔E3, W10↔E4, W11↔E5, W12↔E6, W13↔E7). Текущая контрольная Android-версия: **0.2.0-demo**, демонстрационная, с mock-данными. **Запрещено** изменять ее код или заявлять об интеграции с реальными гидропостами до отдельного теста и согласованного релиза.

## 2. Итоговая цель и границы

Создать независимый от Canva поддерживаемый веб-продукт «Прогностика» (адаптивный desktop/tablet/mobile), который со временем объединит научный контур, управление проектом, эксплуатационный WebGIS, историю данных, защищенный API и согласованный доступ из Android/Telegram.

**Ближайший проверяемый результат:** отдельный репозиторий Web, согласованная дизайн-система, работающая тестовая версия с навигацией к четырем сайтам и честной маркировкой демонстрационных данных. **Дальняя цель:** единый Core с подтвержденными источниками наблюдений, научными расчетами и управляемым жизненным циклом данных. Реальные прогнозы, действующие оповещения, интеграции ГТС/SCADA и показатели точности не считаются существующими и не обещаются до валидации.

## 3. Архитектурные ограничения и предварительный стек

Планируемая схема: `Web UI / Android / Telegram -> versioned Core API -> ingestion/QC/catalog -> PostgreSQL/PostGIS + object storage -> forecast/analysis services`, общие учетные записи и роли после отдельного аудита прав.

**Предлагаемый стек (утвердить после W7, не трактовать как выбранную реализацию):**
- Web: React + TypeScript + Vite; routing; дизайн-система с токенами и компонентными тестами; адаптация, WCAG 2.2 AA как целевой уровень.
- Карта: MapLibre GL JS или Leaflet — выбрать по лицензиям, геоданным, производительности и сценариям; CRS и геометрия проверяются по исходным данным. Нельзя заменять истинную географию картинкой.
- API: FastAPI/OpenAPI как кандидат; PostgreSQL/PostGIS; объектное хранилище по необходимости.
- IAM: OIDC, scoped permissions, RBAC/ABAC, secure sessions; **SSO не считать внедренным**, пока нет проверяемого end-to-end теста.
- Размещение: тестовый стенд с HTTPS и CI; провайдер выбирается после сравнения стоимости, экспортируемости, региональных ограничений, резервирования и SLA. Canva не является местом хранения исходников.
- Источник истины: GitHub для кода, CI и релизов; Google Drive для рабочих управленческих документов и научных материалов; ссылки вместо неконтролируемого дублирования.

**Общие инварианты:** никаких секретов в Git, токенов в URL, чисел «от ИИ» в расчетах, недостоверных данных на картах; каждое наблюдение имеет источник, время, единицы, качество и версию; различать DEMO / TARGET / VERIFIED / PRODUCTION; backend — источник истины после его реального появления; операции аварийного управления ГТС за пределами MVP.

## 5. Этапы W6–W13: содержание, зависимости и приемка

### W6 — Инвентаризация и аудит существующей экосистемы (соответствие E0)
**Цель:** техническая карта четырех сайтов, Android и проектных артефактов до любых объединений.
**Зависимости:** Gate G5 для исполнения; получение прав редактора/экспорта сайтов для полного аудита.
**Задачи:** WEB-006-01 — инвентаризация 4 URL, назначение, доступность и владельцы; WEB-006-02 — запрос/получение исходников, экспортов, модели публикации и прав; WEB-006-03 — аудит интерфейса, доступности, маршрутов, ошибок и mobile; WEB-006-04 — матрица REAL/DEMO/TARGET, повторов, данных, рисков и ограничений; WEB-006-05 — план безрискового сохранения существующих сайтов и отката.
**Результаты:** site-inventory.md, audit-report.md, dependency-and-risk-register.md, снимки экрана/протокол проверок.
**Приемка G6:** все четыре URL описаны; различены 4 самостоятельных сайта или подтвержденные дубликаты; источники прав проверены; дефекты классифицированы; дальнейшее решение владельца по каждому активу. При отсутствии исходников — **блокер**, а не вымышленное прохождение этапа.

### W7 — Концепция продукта, UX, интерфейс и проектирование (E1)
**Зависимости:** G6; утверждение пользовательских сценариев.
**Задачи:** WEB-007-01 — роли, сценарии и границы MVP; WEB-007-02 — карта страниц и единое меню «Обзор / Наука / Матрица / План / Демо / WebGIS (проект)»; WEB-007-03 — дизайн-система, mobile-first макеты и состояния пустых/ошибочных данных; WEB-007-04 — прототип кликабельной навигации; WEB-007-05 — ADR решений по React, карте, хостингу, безопасности и доступности.
**Результаты:** PRD, sitemap, UI-spec, ADR-001.., прототип; никаких платных AI-кредитов Canva.
**Приемка G7:** пользователь утвердил роли, UX и scope; ссылки на 4 сайта корректны; макеты показывают четкие маркировки DEMO/TARGET; доступны сценарии 360px/desktop и клавиатурная навигация. Дизайн не обязан быть в Canva.

### W8 — Отдельный Web-репозиторий, сборка и Core-контракт (E2)
**Зависимости:** G7.
**Задачи:** WEB-008-01 — создать отдельный `prognostica-web` (только после согласования), README, лицензии/прав и branch protection; WEB-008-02 — CI: lint/typecheck/unit/build/security checks и review workflow; WEB-008-03 — приложения shell, routing, responsive header/footer, конфигурация окружений; WEB-008-04 — контракт OpenAPI v1, schema registry, статусы демоданных; WEB-008-05 — архитектура Core/IAM/data provenance, spike с тестовым API без ложного заявления production; WEB-008-06 — preview deployment с HTTPS и rollback.
**Результаты:** repo/commits/CI artifacts, работающий preview URL, API proposal, ADR.
**Приемка G8:** clean build из свежего checkout, CI зеленый, клавиатура и mobile проверены, header links работают, секретов в Git нет, roll back описан, договоренности API зафиксированы.

### W9 — Научный контур и контур управления проектом (E3)
**Зависимости:** G8 и права доступа к релевантным материалам.
**Задачи:** WEB-009-01 — страницы Science и источники / методология / воспроизводимость; WEB-009-02 — Matrix с реальными ID статусов задач и ссылками на GitHub; WEB-009-03 — Roadmap и decision log без дублирования SSOT; WEB-009-04 — разграничение научных гипотез, результатов экспериментов и программных демонстраций; WEB-009-05 — экспорт отчета и цепочка provenance.
**Приемка G9:** ссылки и права корректны; задача имеет источник и статус; любые научные метрики доступны только с версией данных и экспериментом, без вымышленных результатов.

### W10 — WebGIS / управление водными рисками (E4)
**Зависимости:** G8, утвержденные наборы слоев, модель качества данных.
**Задачи:** WEB-010-01 — изучить и лицензировать базовые карты и геоданные Есиля; WEB-010-02 — слои бассейна/гидропостов/потенциальных зон риска с provenance и QC; WEB-010-03 — фильтры, легенда, масштаб, время/единицы измерения, доступность; WEB-010-04 — различать уровни/расходы, зоны затопления, сценарии и неопределенности; WEB-010-05 — контуры объектов/событий/отчетов только на подтвержденных данных, без автоматического управления.
**Приемка G10:** интерактивная карта работает на desktop/mobile; для каждого слоя доступны источник, дата и статус; нет смешения демонстрационных и реальных значений; пространственная карта затопления появляется только при наличии подтвержденного расчетного/наблюдательного основания.

### W11 — Связь Web ↔ Android ↔ уведомления (E5)
**Зависимости:** G8, согласованный API/IAM; при необходимости G10.
**Задачи:** WEB-011-01 — контрактная совместимость API с Android; WEB-011-02 — повторно используемые сущности, UTC/timezones и единицы; WEB-011-03 — сценарии авторизации/ошибок/offline read-only; WEB-011-04 — прототип безопасных уведомлений и Telegram только с разрешениями; WEB-011-05 — e2e на staging, отдельные версии и обратимая миграция Android.
**Приемка G11:** контракты/ошибки подтверждены тестами в staging; Android 0.2.0-demo не изменена без отдельного релизного решения; Telegram не рассылает недостоверные реальные тревоги.

### W12 — Интеграция научных моделей и верификация (E6)
**Зависимости:** G8, научный аудит источников, датасетов и заранее зафиксированный план эксперимента.

## 7. Общий реестр задач и порядок контроля

Для **каждой** подзадачи из W6–W13 требуется карточка с полями:
`ID | Программа/этап | Требование/научная задача | Название | Приоритет | Зависимости | Статус | Исполнитель (только по согласованию) | Срок (только по документу) | Результат URL+commit | Тест/критерий | Версия | Решение о приемке`.

**Статусы:** PLANNED → READY → IN_PROGRESS → REVIEW → VERIFIED → ACCEPTED; отдельно BLOCKED и REJECTED. **Выполнено** только при наличии проверяемого результата и решения о приемке. Не использовать фиктивные проценты и даты. Приоритет P0 для Gate G5, безопасности, происхождения данных и потери информации.

**Контроль после каждого изменения:** техническое задание → ветка/PR → тесты → review → ссылка на commit → протокол приемки → обновление карточки и краткого общего статуса. Важные архитектурные решения — отдельный ADR и согласование владельцем. Ответственные и календарные сроки **не назначены**.

## 9. Взаимосвязь с аспирантурой 4.1.5

Сайт Science, каталог данных и расчеты W9/W12 могут обеспечивать доказательную базу по прогнозированию стока и интеграции ДЗЗ, **но только** при подтвержденной постановке научной задачи и настоящих воспроизводимых экспериментах.

Для диссертации необходимы: data provenance, версия кода, ограничения, контрольный baseline, независимая проверка и решение научного руководителя. Дизайн, UI и GitHub сами по себе не являются научной новизной. Решение о реке/теме диссертации в этом плане не подменяется; география MVP платформы сохраняется как рабочая Есиль.

3. **Научные расчёты:** отдельная одобренная модель в воспроизводимом контейнере/пакете → запуск вручную или серверным scheduler после аудита данных → результаты с commit/dataset/model versions, параметрами, метриками и неопределенностью. LLM не рассчитывает уровни воды из свободного текста.
