## 2. РЕЗУЛЬТАТ ПРОГРАММЫ: ПРОДУКТЫ И НЕПРОДУКТЫ

Контуры будущей платформы:
- Prognostica Web — главный адаптивный портал, обзор, новости разработки, единая навигация, научные материалы, Matrix/Roadmap, состояние данных и WebGIS.
- Prognostica Android — самостоятельный мобильный клиент общего API; контрольная демоверсия неизменна до согласованных обновлений.
- Prognostica Telegram — сервис пользовательских команд, проверенных отчетов, подписок и уведомлений; не круглосуточный Colab-скрипт.
- Prognostica Core — доменная модель, API, учетные записи/роли, данные, история, QC, журналы, задачи, источники и вычислительные результаты.
- Prognostica Research — каталог данных и воспроизводимых экспериментов, протоколы научной проверки, публикационные доказательства.
- Prognostica AI — Gemini API для текстовых разъяснений и контролируемого поиска по разрешенному корпусу, не для создания гидрологических чисел или инженерных порогов.

Не входит в стартовый MVP: автономное управление ГТС/SCADA/PLC, неподтвержденные аварийные оповещения, юридически значимые прогнозы без приемки, SSO «на словах», маркетинговые показатели эффективности без эксперимента, платная облачная инфраструктура без бюджета и одобрения.

### Три последовательно принимаемых продукта
R1 = WEB PREVIEW: работающий адаптивный портал + четыре проверенных внешних перехода + версия DEMO + CI + документация.
R2 = CONTROLLED STAGING: Core API, каталог тестовых/разрешенных источников, безопасная учетная модель, WebGIS/Android/Telegram на стенде, автоматические тесты.
R3 = VALIDATED PILOT: проверенные входные данные, воспроизводимые расчеты, документированные ограничения, операторская проверка, мониторинг, возврат версии и отдельное решение о пилоте. R3 не равен безусловному общедоступному production.

## 3. АРХИТЕКТУРА: ЦЕЛЕВАЯ И ФАКТИЧЕСКАЯ

[Web, Android, Telegram] → HTTPS API Gateway / AuthN & AuthZ → Core (FastAPI-кандидат) → PostgreSQL/PostGIS-кандидат → data/source registry, QC, geodata, runs, events, audit.
Отдельно: ETL & scheduler → разрешенные первичные данные / ДЗЗ / наблюдения → QC / snapshots / provenance; reproducible Python compute → ModelRun/metrics/output; Gemini API → explanations от проверенного контекста и разрешенных источников.
GitHub → source control / pull requests / checks / deployments. Google Drive → проектные документы, научные материалы, реестры, канонический комплект и архивы.
Статус этого графа: TARGET ARCHITECTURE. Конкретный API, БД, scheduler, облачный провайдер, карты, безопасность и стоимость выбираются ADR после аудита, а не считаются установленными.

Кандидатский стек:
- Web React + TypeScript + Vite; design tokens; router; charting; component/e2e tests.
- Карта MapLibre GL JS или Leaflet на основании требований, лицензирования источников и мобильных ограничений.
- Backend FastAPI, PostgreSQL/PostGIS, объектное хранилище; OpenAPI, семантическое версионирование контрактов и миграций.
- Security OIDC + RBAC/ABAC в перспективе. До проверки identity-цепочки запрещено писать «единый SSO работает».
- Контейнерные воспроизводимые Python jobs; оркестрация по расписанию управляемым сервисом; CI GitHub Actions.
- Telegram Bot API через webhook с HTTPS / альтернативный polling для ограниченного стенда, секреты только в безопасном менеджере; не Colab 24/7.
- Gemini API: модель/версия, schema validation, safe prompts, retrieval boundary, hallucination tests, лимиты, fallback, журнал.
- Environment: LOCAL / DEMO / STAGING / PILOT / PRODUCTION; каждая среда, ее dataset и ограничения должны быть наглядны.
Выбор платных платформ, региона хранения, telemetry/личных данных и лицензий требует отдельного ADR и расчета бюджета.

## 4. СЛОВАРЬ ДАННЫХ, КАЧЕСТВО, ОБМЕН

Минимальные сущности будущего Core:
SOURCE (источник, владелец, права, URL, лицензия, дата);
DATASET_VERSION (география, период, формат, checksum, CRS, пространственный/временной шаг, статус QC);
STATION/LOCATION (уникальный ID, координаты, datum/elevation, проверка геопривязки);
OBSERVATION (station_id, observed_at UTC, ingested_at UTC, parameter_code, value, SI unit, flag QC, source_id, dataset_version, missing reason);
EVENT/SCENARIO (type, time period, version, confirmed/demonstration);
MODEL_VERSION (code commit, params, method, training/holdout restrictions);
MODEL_RUN (input dataset versions, config, started/finished, outcome, logs, warnings);
FORECAST (run_id, horizon, target, value, interval/uncertainty if method supports it, validity, QC);
FLOOD_GEOMETRY (только с независимым пространственным расчетом/наблюдением и CRS/provenance);
ASSET/RISK (инфраструктура, законность координат, правила вычисления, экспозиция, ограничения);
TASK/DECISION/REPORT/AUDIT_EVENT (авторизованные изменения и цепочка доказательств);
BOT_SUBSCRIPTION (опционально после privacy review: согласие, scope, канал, выключение).
Не вводить фиктивные значения по отсутствующим постам. INSUFFICIENT_DATA ≠ LOW_RISK. H и Q не смешивать (отметка/уровень, м; расход м³/с). Дата измерения ≠ время загрузки. Аналитические маски затопления ≠ прогноз уровня без 1D/2D или другого обоснованного перехода. ДЗЗ и карты должны иметь лицензию, геометрию, точность и дату.

Предлагаемые API (контракт, не реализация):
GET /v1/health; GET /v1/status; GET /v1/sources; GET /v1/stations;
GET /v1/observations?station=&from=&to=; GET /v1/datasets/{id};
GET /v1/model-runs/{id}; GET /v1/forecasts?station=&run=;
GET /v1/map-layers; GET /v1/reports/{id}; GET /v1/tasks;
POST /v1/subscriptions (после IAM), POST /v1/admin/ingest (служебный scope).
Каждый endpoint описывает в OpenAPI схему, unit, event time, источник, QC, ошибки, privacy, throttling и демонстрационный статус. Публикация протокола не означает доступность сервера.

### Матрица способов запуска
- Код/сборка: commit/PR → GitHub CI → review → artifact. Автоматично после настройки; production deployment только с одобрением.
- Colab: вручную интерактивное исследование; воспроизводимые фрагменты → Python package → cloud job только после review.
- Получение гидроданных: cron/Cloud Scheduler (КАНДИДАТ) по разрешенному расписанию → QC → versioned ingest; ошибка = статус INSUFFICIENT_DATA/STALE, а не «безопасно».
- Модель: ручной или серверный scheduled trigger, фиксированный input+version+log+metrics, вычисления без LLM.
- Gemini: по запросу пользователя либо на событие с permission gate → API → schema/safety/citation test → ответ или безопасный fallback.
- Telegram: внешний event webhook на постоянно доступном сервере → RBAC/consent → Core response. Для старта staging допускается polling; Colab не используй как 24/7 сервис.
- Еженедельный отчет: может быть сформирован автоматикой ТОЛЬКО после настройки trigger и данных; этот документ сам ничего не расписал. Отчет ссылается на фактические commits, issues, datasets, blockers.
- Архивирование: по версии/событию → утвержденный export → Drive + checksum → verify, без перемещения сервисных папок до проверки прав.

### Безопасность запуска
NO AUTO PUBLIC ALERTS; NO AUTO BILLING; NO AUTO GIT PUSH TO PRODUCTION; NO AUTO CHANGE OF IP/AUTHORSHIP/CANONICAL DOCS. Все расписания включаются отдельно и по записи DEC-AUTO-... с владельцем, периодом, scope, лимитами, тестом выключения и обратным откатом.
